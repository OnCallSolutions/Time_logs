# Company registration and tenancy

## Current boundary

Tanovo Time currently provisions one licensed company per application/database deployment. The company is bound by `COMPANY_CODE` and `COMPANY_NAME`; its operational tables are not yet consistently scoped by a tenant key. Do not register a second customer in the current operational database or treat a company code as an authorization boundary. Keep `DEVONCALL` / `DevOnCall` as this deployment's company.

This is a preparation framework, not a claim that multi-company production onboarding is already enabled. The first safe licensing model is a deployment stamp per customer: shared application source, isolated production database and configuration per company. A future shared application may use a database pool, but only after tenant isolation is present and tested across every data path.

## Registration lifecycle

Use an explicit state machine for each prospective customer:

`draft -> requested -> verified -> provisioning -> active -> suspended -> retired`

Failed or withdrawn requests become `rejected` or `cancelled`, retaining an audit record. A request must not become `active` merely because a user authenticated with Microsoft or supplied a domain name.

Company registration should capture:

- Immutable internal `company_id` UUID, generated by the service.
- Unique immutable `company_code` and normalized URL-safe slug.
- Official legal/display names, billing contact, region, and requested plan.
- One or more verified email domains, while allowing approved exceptions such as personal Gmail during initial setup.
- Microsoft Entra directory tenant ID after an authorized organization administrator completes consent and verification.
- Lifecycle state, timestamps, provisioning owner, and audited state transitions.
- A secret-manager reference for database credentials; never store raw connection strings or client secrets in company rows.

Keep customer-issued employee/contractor IDs distinct from Tanovo Time's immutable account UUID and company-scoped human reference. Names, roles, employee IDs, domain checks, and settings belong to a company membership, not to a globally shared person's record.

## Provisioning flow

1. A prospective company submits a bounded registration request; the request is rate-limited and remains inactive.
2. A platform operator reviews the company identity, plan, domain evidence, and authorized setup contact. Domain matching is a warning/verification input, not proof of legal authority.
3. The company's Microsoft Entra administrator completes the tenant-consent flow. Validate the signed token's tenant ID and issuer server-side, then bind that directory to the registered company. Do not trust a tenant ID supplied only in a browser form.
4. Provision an isolated database and application configuration for the company. Apply versioned migrations, create the first company administrator through a one-time enrollment link, and verify that the admin can reach only that company's data.
5. Run isolation, backup/restore, authentication, and onboarding smoke tests before changing the registration to `active`.
6. Record every status/configuration change in the platform audit log. Suspending or retiring a company blocks new sessions and preserves records according to the approved retention policy.

## Data and identity architecture

### First licensing release: isolated deployment stamps

Use one production database per company, with separate credentials and environment configuration. The current singleton `licensed_company` and deployment-bound `COMPANY_*` configuration fit this model. The platform registry should be a separate control-plane store, not a table in a customer's operational database. A registry record may contain a database/resource identifier, but credentials remain in a secret manager and are only retrieved by a trusted provisioning/runtime identity.

This makes the first customer onboarding simpler to secure and lets us keep the current single-company query model. It adds provisioning, migration, observability, and support work per customer; automate those operations before growing the customer count substantially.

### Later shared application / database pool

Before sharing an operational database, add `company_id` to every company-owned table and compound every uniqueness rule with it. Resolve a company from a verified identity/domain/explicit organization selection, then create one immutable request context; never infer the tenant from an untrusted row ID or arbitrary request header. Scope reads, writes, joins, audit events, background jobs, AI context, message delivery, exports, and caches to that context.

For Postgres, use row-level security as defense in depth, with default-deny policies and a database role that cannot bypass RLS. Application predicates still need explicit tenant scope. Test cross-company read, update, delete, search, export, and guessed-ID access for every API family. A missed query or cache key can otherwise disclose another company's records. PostgreSQL notes that table owners typically bypass row security, so runtime credentials and migration ownership must be separated and tested.

### Entra identity

Microsoft Entra directory tenants and Tanovo Time customer companies are separate concepts. If the product later accepts multiple customer directories, Entra must be configured for a multitenant audience and the callback/token validation must support multiple issuers. First sign-in must not grant app membership automatically: require verified company registration, an allowed tenant ID, and an approved invitation or company-admin enrollment. Keep the current single-tenant sign-in behavior until the multi-tenant identity flow is implemented and tested end to end.

## Platform control-plane records (future schema)

The registration service should own a small registry with fields similar to:

```sql
CREATE TYPE company_registration_state AS ENUM (
  'requested', 'verified', 'provisioning', 'active', 'suspended', 'retired',
  'rejected', 'cancelled'
);

CREATE TABLE platform_companies (
  company_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  company_code text NOT NULL UNIQUE,
  slug text NOT NULL UNIQUE,
  legal_name text NOT NULL,
  display_name text NOT NULL,
  entra_tenant_id uuid UNIQUE,
  state company_registration_state NOT NULL DEFAULT 'requested',
  isolation_stamp text,
  database_secret_ref text,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE platform_company_domains (
  company_id uuid NOT NULL REFERENCES platform_companies(company_id),
  domain text NOT NULL,
  verified_at timestamptz,
  PRIMARY KEY (company_id, domain),
  UNIQUE (domain)
);
```

This is a design sketch, not a migration to run in the current customer database. The eventual control plane also needs registration contacts, plan/subscription state, immutable transition audit, idempotent provisioning jobs, and a safe company-admin bootstrap flow. Domain ownership can be verified with DNS challenge tokens; never treat an email suffix alone as tenant proof.

## Required release gates

- Threat model covers company discovery, signup abuse, tenant switching, stale sessions, role assignment, invitations, data exports, and support/admin access.
- Tenant identity is immutable for a request and included in authorization decisions and data access.
- Automated cross-tenant denial tests cover every route, repository helper, message/AI path, and cache.
- Database migrations can run repeatedly and safely across customer stamps, with a tested rollback/restore procedure.
- Secrets, logs, analytics, error reports, email delivery, and AI prompts are tenant-scoped and avoid cross-customer data leakage.
- Suspension/revocation propagates to active sessions and any background jobs.
- Company deletion/retention, data residency, backup, restore, and customer export policies are defined before paid onboarding.

## Research baseline

The first-release recommendation is an isolated database per company, then reassess a shared database or database pool against customer count, isolation requirements, operations cost, and restore needs. Microsoft describes tenancy as a spectrum with security, cost, and operational tradeoffs, and cautions that a shared database needs deliberate tenant scoping. PostgreSQL RLS can enforce row policies but is default-deny only after enabled and can be bypassed by table owners. Entra multitenant app registration changes the sign-in audience and requires handling multiple issuers and admin consent; it does not itself establish Tanovo Time membership.
